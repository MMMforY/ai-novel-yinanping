# AI 小说「意难平」项目

> **故事不该这样发生？那就改掉这一幕。**

这是一个面向中文故事消费者的 AI 小说 / 故事改写产品探索项目。

## 本地网页版 MVP

已实现「迭页」的本地响应式网页：导入 / 创建故事 → 阅读 → 选中文字 → 改写这一幕 → 保存世界线 → 继续阅读 / 返回原版。

### 启动

使用 Node.js **22.22.2 或更新版本**（本次验证环境为 22.23.1）：

```bash
npm install
npm run dev
```

打开 **[http://localhost:5173/](http://localhost:5173/)**。一个命令会启动网页和本地模型代理。Windows PowerShell 中也可以使用 `npm.cmd install` 和 `npm.cmd run dev`。

没有模型配置时，页面明确标注「演示模式」。可点击「体验原创演示」，或在导入页填入原创示例「雨停之前」，选中栈桥断裂的片段，输入「让她活下来」，完成第一条世界线。

### 配置真实模型

将 [.env.example](./.env.example) 复制为仓库根目录下的 `.env`，填写以下服务端变量，然后重新启动 `npm run dev`：

```dotenv
LLM_BASE_URL=https://your-provider.example/v1
LLM_MODEL=your-model
LLM_API_KEY=your-api-key
```

模型服务需提供兼容 Chat Completions 的 `/chat/completions` 接口。地址填接口前缀，不包含 `/chat/completions`。本地无密钥模型可以留空 API Key，并设置 `LLM_ALLOW_NO_KEY=true`。

默认请求使用 `max_tokens`；需要其他参数的模型可设置 `LLM_TOKEN_PARAMETER=max_completion_tokens`。模型须按提示词输出含 `title`、`text` 的 JSON 对象。接口错误、超时和无效输出都会显示错误，不会自动切回演示模式。部分填写模型配置也不会进入演示模式。

密钥仅由本地 Node 服务读取；`.env` 已被 Git 忽略。生成时，相关上下文会发送给所配置的模型服务。演示模式使用预设片段，不能用来评价真实模型的叙事质量。

### 保存与限制

- 故事、原版、世界线和阅读进度保存在当前浏览器的 **IndexedDB**（数据库 `dieye-local`）。没有账号或云同步。
- 存储按访问地址隔离：`localhost:5173`、`127.0.0.1:5173` 和生产端口的数据互不共享。清除网站数据会删除本地故事。
- 导入上限 30,000 字；TXT 必须是 UTF-8、最多 120KB。首版没有 DOCX 导入。
- 一次选区最多 2,000 字；一个世界线最多 120,000 字。适合先验证故事片段或章节。
- 模型默认发送有限上下文窗口（18,000 字符预算），不是整部小说。人物长期记忆与可靠回归原主线仍需后续验证。
- 字体随项目本地提供，不依赖在线字体服务。

更完整的架构、配置与验收记录见 [本地 MVP 说明](./docs/LOCAL_MVP.md)。

### 验证与生产构建

```bash
npm test
npm run build
npm run test:e2e
```

浏览器测试在独立的 `localhost:5174` 运行，不读写日常开发地址的故事。Windows 若安装了标准路径的 Chrome，将直接使用其独立测试进程；其他环境先运行 `npx playwright install chromium`。

构建后可运行 `npm start`，通过 **http://127.0.0.1:8787/** 访问本地生产版本。这个地址使用独立的浏览器存储，仍会加载根目录 `.env`。

## 一句话产品定义

让读者在遇到小说、动漫、影视等故事中的“意难平”时，用一句自然语言改变关键情节，并继续阅读改变后的故事；在可能的情况下，AI 尽量以最小蝴蝶效应重新接回原有主线。

## 当前核心用户

一个平时天天看番茄小说、脑子里经常幻想剧情，但从来没真正写过小说的 22 岁大学生。

他不是“作者”，而首先是“故事消费者”。产品的目标不是逼他学习写作，而是让他从阅读自然跨越到创造。

## 核心场景

- 喜爱的角色死亡
- CP 没有在一起
- 某个人物被写崩
- 主角做出了用户无法接受的选择
- 结局或关键剧情让用户产生强烈“意难平”

用户最直接的念头通常不是“我要写小说”，而是：

> “这里不应该这样。”
>
> “她不能死。”
>
> “如果当时发生的是另一种可能呢？”

## MVP 原则

第一版先证明一件事：

> 用户是否愿意为了“修复意难平”而使用 AI，并且生成结果是否真的让他产生“我想继续看”的感觉。

MVP 优先支持：

1. 导入已有故事文本 / 剧情摘要
2. 从零开始创造故事
3. 选中或指定“意难平”节点
4. 用自然语言说明希望怎样改变
5. 选择改动强度：最小改变 / 合理改变 / 新世界线
6. 生成改变后的故事并继续阅读
7. 随时回到原版 / 重新改写

## 版权约束

版权风险必须持续作为产品设计约束。

第一版优先使用：

- 用户主动提供的文本
- 用户自己的原创内容
- 获得授权的内容
- 剧情摘要 / 用户描述

不要把“自动抓取或复制受版权保护的小说全文”作为 MVP 默认能力。

## 首个验证场景

以《龙族》中“绘梨衣”的强意难平场景作为产品体验验证案例之一：

> 用户希望“绘梨衣不要死”，同时尽量不把整个故事彻底改写成另一部小说。

此案例用于验证“最小命运干预”是否具有真实的情绪价值与阅读价值。

## 当前阶段

**阶段：本地网页版 MVP → 核心体验验证**

已归档现有 Figma 的 8 张设计画板与节点快照，并在网页中补齐选区、改写弹层、世界线保存和阅读衔接。Figma 在线文件仍保留原有状态。归档详情见 [Figma 设计归档](./docs/design/figma/README.md)。

下一步重点不是扩充功能，而是：

1. 配置模型，用原创故事或用户可使用的文本验证真实改写质量
2. 观察用户是否愿意改变剧情、改完后是否愿意继续读
3. 据实际结果决定长期上下文与因果约束的下一步实现
